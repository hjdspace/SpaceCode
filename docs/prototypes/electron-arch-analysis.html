一、当前问题诊断

核心问题

当前 electron/ 目录有 50 个 .ts 文件直接平铺在根级，涵盖从 CLI 进程管理到桌面宠物、从 Git 操作到 H5 服务器等完全不同的领域。这导致：

症状影响
文件清单不可扫览开发者/AI 需要逐一打开文件才能确定职责
领域边界模糊h5Server.ts 依赖 engineGateway.ts 依赖 engines/，但三者平级
命名前缀化成为事实分组h5*、cron*、mcp*、pet* 前缀已暗示分组，但缺少目录边界
测试路径脆弱../sessionProcess 等相对引用在文件移动后全部需要更新

三、目标目录结构

设计原则：用 codebase-design 的深度模块语言——每个子目录是一个模块，其 index.ts 是接口（小表面），内部文件是实现（大隐藏）。子目录边界即接缝，跨模块引用通过 index.ts 导出而非深路径。保留 engines/、design/、im/、imServer/、proxy/、skillManagerV2/ 等已有子目录不变。

五、深度模块分析（codebase-design 视角）

session/ — 会话生命周期模块

接口：通过 sessionProcess.ts 暴露 SessionProcess 类，controlProtocol.ts 暴露协议编解码函数。

实现：隐藏了子进程管理、协议解析、Bun 路径解析、MCP 配置注入等复杂度。

删除测试：删除此模块 → sessionProcess、controlProtocol、engineChildProcess 复杂度散布到 claudeCodeIPC/h5Server/imServer。通过。

接缝：内部 ./controlProtocol → ./engineChildProcess 是内部接缝；外部通过 ../session/sessionProcess 访问。

engine/ — 引擎适配层模块

接口：engineGateway.ts 是统一深模块入口，engines/ 子目录是引擎工厂。

实现：隐藏了 ClaudeCode/Pi 引擎选择、进程池、CLI 检测、SDK 安装等。

依赖类别：In-process（EngineFactory）+ Local-substitutable（进程池可 mock）。

infra/ — 基础设施模块

角色：被所有其他模块依赖的横切关注点。

内容：logger、platform setup、proxy manager、front-matter parser、auto-updater。

注意：logger 被 ~15 个文件引用，是依赖密度最高的模块。移入 infra/ 后，引用从 ./logger → ../infra/logger。

tools/ — 外部工具集成模块

角色：各种外部二进制工具的安装、探测、MCP 调用。

内容：OfficeCLI、CUA Driver、Browser-Use、MCP 配置/探测、RTK。

删除测试：删除后 → 9 个文件的安装/探测/管理逻辑散布到 main.ts。通过。

六、实施计划

执行顺序

  1. 创建子目录：infra/ session/ engine/ git/ h5/ cron/ tools/ skills/ pet/
  2. git mv 移动文件：用 git mv 保留历史
  3. 更新 electron 内部 import：相对路径 ./logger → ../infra/logger 等
  4. 更新测试 import：electron/__tests__/ 和 tests/electron/ 下的引用
  5. 更新外部引用：src/services/h5WebSocketClient.ts → h5Types.ts 路径
  6. 更新 main.ts/preload.ts imports：根入口文件的 import 路径
  7. 运行 build + test 验证
