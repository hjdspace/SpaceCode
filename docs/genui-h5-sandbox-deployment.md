# H5 卡片沙箱的第二端口 — 部署与排查

适用范围：H5 远程访问里渲染 GenUI 卡片的那第二个 HTTP 服务。口径见 `docs/adr/0015-genui-card-sandbox-origin.md` 第 2 条、
`docs/prd/genui-cards.md` §7 与 GitHub Issues 上的票 06「H5 端沙箱承载与部署」。

## 1. 它是什么

启用 H5 后，主进程在 H5 主服务端口之外再起**一个只读静态服务**：

| | 主服务 | 第二端口（沙箱） |
| --- | --- | --- |
| 端口 | `fixedPort` 或系统分配 | **主端口 + 1**，可在设置里显式指定 |
| 内容 | SPA 文档、`/api/*`、`/ws` | 只有 `dist/genui-sandbox/` 里的四个产物文件 |
| 鉴权 | Token（`?token=` 或 `Authorization`） | 无 —— 静态产物不含用户数据 |
| 引擎 / 会话 | 可读写 | 完全不接 |
| 目录列举 | 无 | 无 |

浏览器把每张卡片渲染成 `<iframe sandbox="allow-scripts">` 指向第二端口的 `/index.html`。
第二端口与主服务**同 site、不同 origin**：卡片读不到父文档、读不到主服务的存储，
但**没有**桌面端那样的 OOPIF 进程隔离（见第 5 节残余风险）。

## 2. 必须把两个端口一起暴露

第二端口只提供静态资源，所以它没有 API 可"绕"，也没有别的端口可替补：

- **只暴露主端口 = 卡片全部报错**。两种说法要分清：
  - 第二端口在这个进程里就没绑定成功 → 服务端不广播沙箱源，卡片显示"当前宿主未接入卡片沙箱"；
  - 第二端口绑上了、但浏览器连不通（代理没暴露、防火墙拦下、产物缺失）→ 卡片显示
    "卡片沙箱源无法访问：H5 部署请确认第二个端口已随主端口一起暴露"。
- 反向代理/端口转发要按 **`主端口 → 主端口+1`** 的同一关系映射。服务端逐响应把沙箱源写进
  父页面的 `frame-src` 和一个带 nonce 的内联引导脚本，两处出自同一次计算：
  - 端口来自浏览器实际看到的地址（`Host` 头）或运维配置的"公网访问地址"；
  - 因此**代理保留 Host** 时，直连、`ssh -L` 隧道、端口型反代都能自动对上；
  - 代理把主服务映射成别的对外端口时，请用"公网访问地址"填上对外地址，并在需要时显式设置沙箱端口。
- **https 站点必须给沙箱源也是 https**。页面是 https 而沙箱源是 http 时浏览器会按混合内容直接拦掉，
  卡片会明确报"沙箱源无法访问"。给第二个端口配同一张 TLS 证书，或让反代在同一主机名下按同样的
  TLS 终止它。
- 端口被占用时**不自动漂移**：主服务照常起来，第二端口标记为"未监听"（设置页会显示），
  卡片退化成错误态。漂移了父页面就不知道该 frame 谁。这时服务端连沙箱源都不广播，
  卡片立刻显示"未接入"，不会先亮 5 秒空白 iframe 再换成握手超时。
- **第二源只能落在同一个主机名上**：算出来的源始终是"页面用的主机名 + 某个端口"。
  把沙箱放到另一个主机名或子域名（`sandbox.example.com`）不在本票范围内。
- **同源不算第二源**：沙箱端口配成与主服务一致（`443`/`80` 也算一致）时渲染端会直接拒绝它 ——
  同源 iframe 不是沙箱（ADR 0015 备选方案第一条）。

## 3. 配置项

设置 → H5 远程访问 → 高级设置：

- **卡片沙箱端口**：留空 = 主端口 + 1。改动在**重新开启 H5** 之后才生效（第二端口随主服务一起绑定）。
- **公网访问地址**：填了就以它的主机与协议为准来算沙箱源，不再看 `Host` 头。

对应持久化字段是 `h5-access.json` 的 `sandboxPort`（旧文件缺该字段时按"主端口 + 1"处理）。

## 4. 排查顺序

1. **设置页 → 服务器状态**：看"沙箱端口"是否显示"未监听"。是 → 该端口被别的进程占用，
   换个显式端口再重开 H5（`netstat -ano | findstr :8081` / `lsof -i :8081`）。
2. **直接开第二端口**：浏览器访问 `http://<主服务地址+1>/index.html`，应看到
   `waiting for host handshake…`。看到连接失败 → 端口没暴露或被防火墙拦；
   Windows 首次启用 H5 要在防火墙提示里放行 SpaceCode。
3. **看卡片自己的报错文案**（只影响那一张卡）：
   - "当前宿主未接入卡片沙箱" → 文档没带上注入的源：第二端口没绑定成功（先看第 1 步），
     或者 `dist/index.html` 是旧构建、代理改写了 HTML 响应体。前者重开 H5，后者重新
     `npm run build` 并确认代理不替换正文。
   - "卡片沙箱源无法访问…" → 第二端口连不通，或 https 页面配了 http 源。
   - "卡片未能与宿主完成握手" → 第二端口通、文档加载了，但卡片没能和宿主说上话：
     检查沙箱产物是否完整（`sandbox.js`、`sandbox.css`、`sandbox.theme.css` 都要在
     `dist/genui-sandbox/` 里，构建命令 `npm run build:genui-sandbox`）。
   - "卡片协议版本与当前版本不一致" → 会话里存的是别的版本的卡片，属正常降级。
4. **开发者工具的 Console**：被 CSP 拦掉会写明是哪条指令拦的。父页面的 CSP 是**逐响应下发**的
   （响应头与文档里的 `<meta>` 同值），所以看到 `frame-src` 报错时，先确认浏览器拿到的
   是最新响应而不是缓存 —— 文档带 `Cache-Control: no-cache`，正常应当回源。

## 5. 残余风险（接受，不是待办）

- **只有跨 origin，没有进程隔离**：第二端口与主服务同 site，恶意卡片里的死循环会拖住同进程的页面。
  桌面端由 OOPIF 隔离，H5 端不做（PRD Out of Scope 明确排除）。
- **卡片不能外联**：沙箱文档的 `connect-src 'none'`，网络请求、表单提交、顶层导航、新窗口全被拦；
  外链只走 `openLink` 白名单（绝对 `http:`/`https:`）。
- **父页面 CSP 永不带 `unsafe-eval`**：`unsafe-eval` 只存在于沙箱源。父页面的 `script-src`
  是 `'self' + 当次 nonce`，那个 nonce 只授权注入沙箱源的一段引导脚本。
- **第二端口不带鉴权**：它服务的四个文件是构建产物本身，公开可读；一旦有人能读它们，
  也能从主服务的静态目录里读到同样的东西。不要往 `dist/genui-sandbox/` 放任何私有内容。
- **可达性探测**：卡片超时后父页面会用 `mode: 'no-cors'` 探一次沙箱源，只能得到"有没有回应"，
  读不到响应内容。这是为了把"端口没暴露"和"卡片自己起不来"分开，代价是父页面的
  `connect-src` 保留对 `http:`/`https:` 的放行（与改造前一致，未额外放宽）。
- **H5 剪贴板**：非安全上下文（用 IP 直连的 http 页面）里浏览器没有 Clipboard API，
  卡片复制会给出"复制失败，请稍后重试"。这是浏览器限制，不是沙箱拦的。
